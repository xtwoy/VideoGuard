# VideoGuard-E 参赛材料目录、阅读路径与事实口径

> **文档性质：** 内部材料导航与一致性管理文件，不代替赛事平台的正式提交要求。它负责说明每份材料要解决什么问题、评审者应先读什么，以及哪些项目事实不能在不同文档中被写成不同版本。

## 一、这套材料如何阅读

**正式主稿：** [`docs/10_参赛作品报告.md`](../10_参赛作品报告.md) 负责统一叙述、图号、实验结论和最终 PDF 的正文来源。这里的 00—09 是分工明确的素材/附件文档，不建议把十份 Markdown 连续拼接为 PDF。定稿时应先修订主稿，再回写相关配套材料，防止两套口径漂移。

本目录中的文档是分工明确的配套材料，不应把每一份都当作独立的完整论文。项目简介、设计方案和测试验证是技术正文的核心；演示脚本服务于讲解；截图清单和数据图注规范用于制作证据图；复现说明用于让第三方按步骤运行；提交前检查用于最终验收。

| 文件 | 主要读者 | 必须回答的问题 | 推荐用途 |
|---|---|---|---|
| 01_项目简介.md | 初次阅读的评审者 | 为什么做、解决什么问题、贡献是什么、证据边界是什么 | 报告开篇与摘要扩写依据 |
| 02_设计方案.md | 技术评审者 | 系统如何分层、PEAD 怎样工作、失败时怎样处理 | 报告技术主体 |
| 03_测试与验证.md | 关注研究可信度的评审者 | 实验怎样设计、结果说明什么、哪些结论不能推出 | 报告实验与局限章节 |
| 04_演示脚本.md | 答辩人和现场操作者 | 展示顺序是什么、每一步要讲什么、出现问题如何处理 | 现场演示与答辩排练 |
| 05_截图清单.md | 文档排版和截图制作人员 | 哪些图片值得保留、图片来源是什么、图注如何写 | PDF 配图制作和验收 |
| 06_提交前检查.md | 全体团队成员 | 哪些信息必须确认、什么检查未完成、如何冻结交付版本 | 定稿前签核 |
| 07_运行与复现说明.md | 评审者、验收人员、未来维护者 | 怎样安装、启动、运行演示与复核结果 | 程序包附件与验收 |
| 08_演示数据与图注规范.md | 报告作者、答辩人 | 合成数据、真实 UI、机制图分别能证明什么 | 防止过度宣传与错误图注 |

**建议阅读顺序：** 01 → 02 → 03。若要现场演示，再读 04；若要制作 PDF，结合 05 与 08；最后按 06 验收，并按 07 复现。

## 四、版本、数字与证据的管理规则

1. **最终 commit 以实际交付为准。** 不要将旧的开发基线、展示截图 commit 或历史验证 commit 写成最终交付版本。最终验收时记录 commit SHA、日期、执行环境和每条命令的退出状态。
2. **测试数量不能脱离运行记录。** 249 项是当前参赛材料记录的后端测试规模；代码变化后必须重新运行。历史自查报告中的 169 项特定测试、5184 个不变量组合、512 个三节点攻击图核对和 36/36 HTTP/ffprobe 检查属于另一份特定环境记录，不能直接相加。
3. **静态检查不能写成真实效果实验。** 30 项 Prompt 契约检查验证部分字段/枚举约定，不验证模型是否遵循 Prompt。
4. **图片必须标注证据类型。** 正文和图注需明确它是真实 UI 截图、合成输入的系统结果、独立工程 fixture 机制图，还是合成示意。
5. **未确认的信息保留占位并阻止提交。** 团队分工、AI 工具名称、最终日期、赛事要求等信息由团队确认；不允许用猜测填满表格。

## 五、推荐交付工作流

1. 核对赛事当期的正式模板、页数、匿名、文件大小、命名、声明与程序包要求。
2. 以 01—03 为内容底稿，整合成连续、完整的参赛作品报告；不要把每份材料的标题和摘要简单拼接。
3. 根据最终 UI 重新截取界面图，检查机制图和实验数字，统一图号与图注。
4. 在最终代码 commit 的干净环境中执行 07 中的安装、测试和演示步骤。
5. 完成 06 的内容、技术、视觉、合规与提交验收；所有未完成项都必须有明确处理结论。
6. 冻结最终 PDF、程序包、提交声明和 commit SHA，保存 SHA-256 与提交回执。
