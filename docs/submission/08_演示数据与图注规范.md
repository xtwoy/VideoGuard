# VideoGuard-E：演示数据来源、证据等级与图注规范

> **本文件是参赛材料的证据口径规范。** 它的目的不是限制展示，而是确保每张图、每个数字和每段案例叙述都准确说明来源。只要数据来自人工编写的合成输入，就必须在正文或图注中明确写出，不能把它描述为真实视频模型识别结果。

## 一、为什么要区分数据类型

审核系统的输出可能同时包含机器观察、人工编写的冻结输入、规则计算结果和 UI 渲染结果。这些对象的证据地位不同：

- 机器观察是上游模型对内容的报告，不自动等于独立核实的事实。
- 合成输入是为测试某个机制而人为定义的事实、事件和关系回答，适合检查程序行为，不适合衡量真实视频性能。
- PEAD 输出是当前输入、规则版本和求解器共同产生的裁决，能证明代码在该输入下如何执行。
- UI 截图能证明界面如何呈现某条记录，不能单独证明输入事实真实。
- 人工标注的真实视频评估集，只有在视频授权、标注规则、标注过程和评价指标都明确后，才可用于估计真实效果。

如果将这些类型混在一起，报告就会从“机制验证”误写成“性能评估”，从而超出当前证据支持的范围。

## 二、仓库中主要数据来源

| 数据类型 | 仓库位置 | 如何产生 | 可支持的主张 | 不能支持的主张 |
|---|---|---|---|---|
| 工程回归用例 | backend/fixtures/cases.py、backend/fixtures/cases/ | 人工维护源定义，生成静态 JSON，再通过项目校验器 | 指定输入下的规则和回归行为 | 真实视频的代表性、准确率或泛化 |
| 五套参赛展示场景 | backend/fixtures/showcase.py、backend/fixtures/showcase/ | 人工撰写场景事实、口播、时间和期望结果，走正式 PEAD/报告校验链 | 具体合成故事下的系统结果和界面流程 | 模型实际看过对应真实画面 |
| 冻结上游快照 | backend/fixtures/ 与 backend/reports/mock-pead-inputs.json | 固定阶段一/二/三的结构化输入 | 在同输入条件下比较决策分支 | 上游模型在真实环境中的输出分布 |
| 真值表 | backend/reports/pead-truth-table.md、.json | 脚本枚举关系回答组合 | 当前 fixture 与枚举范围内的决策行为 | 所有可能视频输入都已穷举 |
| 同输入对照 | backend/reports/mock-pead-comparison.md、.json、.csv | 相同输入分别经过有/无 PEAD 分支 | 指定合成场景的决策差异 | 真实准确率提升或统计显著性 |
| 论证机制图 | backend/reports/pead-argumentation.html、.md | 独立工程 fixture 构造论证节点与攻击关系，实际调用求解器 | 论证生成、攻击边、grounded 标签和解释 | 该图来自五个展示场景之一的同次运行 |
| UI 截图 | docs/assets/demo/ | 生产前端在指定本地记录上渲染并截图 | 某个版本界面的信息组织方式 | 真实模型的识别正确率 |
| 真实模型回包 | 只有配置密钥并实际调用后才存在 | 外部模型服务返回结构化数据 | 指定调用的实际返回内容 | 未经人工核验的事实真伪或总体模型性能 |

## 三、五套展示案例的完整口径

### 案例 A：天台危险动作与鼓励模仿

**合成故事：** 人工定义的分镜事实描述一名男子翻越高处护栏、跨越楼间空隙，随后口播“你们也试试，胆大一点就行”。动作与口播在结构化输入中被定义为同一事件，并给出鼓励同一事件的关系回答。

**演示目的：** 展示当事件作用域、关系回答和其他必要条件都支持危险行为诱导时，PEAD 可以生成 SUPPORTED / FLAG，并将依据保留在审核结果中。

**允许的结论：** 在这组合成输入下，PEAD 与报告校验链生成了预期的风险提示。

**不允许的结论：** 不得说“模型从真实视频识别出男子跨楼”“系统已验证真实危险动作识别准确率”，也不能说这一案例证明了对所有危险行为都有效。

**推荐图注：** 图 X. 天台危险动作与鼓励口播的合成输入结果。案例由人工编写，PEAD 与报告校验代码实际执行；不是模型对真实视频的识别结果。

### 案例 B：同一动作与明确劝阻口播

**合成故事：** 保持案例 A 的危险动作描述不变，将口播替换为“千万别学我，这里没有任何防护，摔下去就是重伤”等明确警示内容。

**演示目的：** 控制动作变量、改变语境变量，展示系统需要处理警示而不是仅根据危险画面或关键词累计风险。

**允许的结论：** 在当前合成观察与策略范围内，危险行为诱导策略不应仅因出现危险动作就直接认定为鼓励诱导；具体输出以最终生成报告为准。

**不允许的结论：** 该策略的 NOT_SUPPORTED / NONE 不等于跨楼动作安全，也不代表视频符合全部平台规则或必然可以发布。画面仍可能触发其他风险策略。

**推荐图注：** 图 X. 固定危险动作、将口播改为明确警示的合成对照。该对照用于解释证据关系对危险行为诱导裁决的影响，不构成真实视频安全认证。

### 案例 C：跨事件错误关联

**合成故事：** 一个事件描述厨房中跳过燃烧灶眼的动作，另一个事件描述户外骑行并出现“这个动作我练了三个月，别模仿”等话语。冻结输入人为注入错误关系回答，将两个不同事件关联为同一事件。

**演示目的：** 检查模型关系回答是否受到事件指向与证据作用域的约束。PEAD 不应仅凭高置信关系回答直接生成强风险提示。

**允许的结论：** 当输入中已经明确包含不同事件的结构化指向时，PEAD 可以利用这一矛盾阻止该关系直接成为强支持，并将结果转为冲突/人工复核。

**不允许的结论：** 不得声称真实上游模型已经发生该错误，也不得声称 PEAD 能自动修复上游没有提供的事件标识或错误事实。

**推荐图注：** 图 X. 构造性跨事件误关联输入下的冲突处置。模型关系回答与事件作用域不一致时，系统保留复核；该图不代表真实模型错误发生率。

### 案例 D：手机屏幕中的身份证照片

**合成故事：** 人工编写的开箱场景中，手机屏幕被描述为显示身份证正面照片；后续口播提到“后面会打个码”。

**演示目的：** 展示个人隐私暴露线索如何关联到屏幕文字/图像模态、时间范围和整改建议，特别是不能因为稍后承诺打码就忽略此前可能已经出现的暴露片段。

**允许的结论：** 在这组合成阶段数据下，报告可以呈现疑似隐私线索及遮挡姓名、号码区域的建议。

**不允许的结论：** 不得声称系统已从真实身份证照片中读出姓名或号码；不得在参赛文档中展示未经授权的真实证件内容。

**推荐图注：** 图 X. 合成隐私线索下的证据定位与遮挡建议。画面事实为人工编写的结构化输入，并非真实证件图像识别结果。

### 案例 E：柯基宠物日常负例

**合成故事：** 柯基追球、休息，口播只介绍日常生活，没有预先定义的风险线索。

**演示目的：** 检查无风险线索时系统是否避免无依据地生成风险，并强调“当前未发现某类线索”仍不是视频整体安全保证。

**允许的结论：** 当前合成输入下，没有形成所覆盖策略的风险线索。

**不允许的结论：** 不得把一个干净负例说成已经验证了真实视频误报率，也不得宣称系统对任意安全视频都不会误报。

## 四、工程回归样例与展示案例不可混用

工程回归用例用于固定程序行为和历史缺陷；展示案例用于讲解故事与界面。两者目的不同：

- 18 套工程回归用例覆盖十类策略与若干边界条件，源定义由 cases.py 维护。
- 5 套展示案例专门撰写场景叙述和展示报告，由 showcase.py 维护。
- 论证机制图使用独立工程 fixture，不属于上述五套展示案例的同次运行。
- 不能将 18 套用例 + 5 套展示案例合称为 23 个真实测试视频。
- 不能用生成后的实际输出反推人工期望值；期望值应由测试设计维护。

## 五、实验数字的图注与正文口径

### 5.1 64 种关系回答组合

推荐表述：

“在 7 个含候选对的合成用例上，对四类关系回答进行穷举，共得到 64 种组合，并检查当前决策函数的全定义性、确定性、协议合规和指定保守性。”

禁止表述：

- “穷举了所有可能的视频输入。”
- “证明了算法对所有情况都安全。”
- “64 组测试证明准确率达到 100%。”

### 5.2 十场景同输入对照

推荐表述：

“在 10 个预先构造的合成场景中，无 PEAD 分支有 8 个符合合成处置预期，有 PEAD 分支有 10 个符合。该计数用于说明指定输入下的机制差异，不是独立人工标注的真实视频准确率。”

禁止表述：

- “真实准确率由 80% 提升到 100%。”
- “误报率降低三分之二。”
- “证明 PEAD 在生产环境中优于所有大模型方案。”

### 5.3 论证攻防图

推荐表述：

“图展示独立工程 fixture 下的论证节点、攻击边和 grounded 标签；该页面由实际代码对合成输入生成，用于检查机制行为。”

禁止表述：

- “这是前述真实视频的完整推理过程。”
- “模型已经在真实视频中产生此错误。”
- “grounded 标签是本团队原创算法。”

## 六、图注中必须出现的来源标签

根据图片来源选择一种或多种标签：

- **合成输入的系统结果：** 输入事实由人工编写，程序执行真实。
- **独立工程 fixture：** 与展示故事分离的机制测试。
- **真实 UI 截图：** 截图来自实际运行的前端，但内容可能仍为合成记录。
- **合成示意图：** 为解释架构或流程而绘制，不是程序输出。
- **真实模型回包：** 只有确实发生真实 API 调用并有可核查记录时才能使用；还需说明未经人工核验的边界。

## 七、截图来源与重建方法

仓库当前截图位于 docs/assets/demo/，具体内容和生成方式见 docs/13_演示场景与截图说明.md。离线报告包位于 backend/reports/demo-showcase/。若前端代码在截图之后发生变化，应重新运行展示捕获流程并更新图片，不要把旧截图称为最终界面。

生成/更新展示数据时，应遵循以下顺序：

1. 先写清楚场景事实、事件指向、口播立场和时间范围；
2. 明确每个案例要检验的假设和预期处置；
3. 运行正式 PEAD 与报告校验链路；
4. 检查证据 ID、时间、原因码、处置与报告字段一致；
5. 保存输入摘要、生成版本和输出文件；
6. 重新截图并核对 PDF 图注；
7. 若输出不符合预期，记录为发现的差异并修复实现/测试，不要为了图好看而修改事实或隐藏冲突。
