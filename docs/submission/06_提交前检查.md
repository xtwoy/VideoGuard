# VideoGuard-E：参赛提交前验收与冻结清单

> **使用原则：** 本清单用于阻止“文档看起来完成，但关键事实、图注、环境或提交项没有核实”的情况。方框只有在实际完成并留下可核查记录后才能勾选。不得把计划执行的检查写成已完成。

## 一、赛事要求与团队信息

### 1.1 赛事正式要求

- [ ] 从赛事官方平台确认本届作品提交项、截止时间、PDF 页数/大小、文件命名、程序包格式和声明表。
- [ ] 核实评审材料是否要求匿名；如需匿名，检查 PDF、文件名、封面、图片和元数据中是否出现学校、导师、队员姓名或其他身份信息。
- [ ] 确认是否需要单独上传源代码链接、可运行程序、演示视频、说明书、原创性声明或 AI 使用声明。
- [ ] 不把往届模板或自行推测的要求当作本届正式要求；若官方规则不明确，记录待确认事项。

### 1.2 团队信息

- [ ] 作品名称、赛道名称和报名系统中的信息完全一致。
- [ ] 队长、队员、指导教师等信息由团队确认。
- [ ] 每项核心工作包的负责人、实际贡献与分工比例由团队确认，不自动推断。
- [ ] AI 辅助开发说明符合赛事要求，补齐所用工具名称、版本、使用范围与时间范围。
- [ ] 第三方依赖、开源许可、引用文献和图片/视频素材授权已核对。

## 二、技术事实与数字口径

- [ ] 报告中的版本号和最终 Git commit 与实际提交代码一致。
- [ ] 不沿用过期的开发基线或截图生成基线作为最终交付 hash。
- [ ] 在最终 commit 的干净克隆中重新运行完整后端测试，并保存日志与退出状态。
- [ ] 重新运行 fixture 生成检查、18 套用例验证、Prompt 契约、真值表、论证报告、同输入对照和 HTML 一致性检查。
- [ ] 重新运行前端 TypeScript 检查与生产构建。
- [ ] 若声明真实视频上传路径可运行，确认 ffprobe 在目标环境可用并运行 HTTP/ffprobe 冒烟检查。
- [ ] 将执行环境、Python 版本、Node 版本、操作系统、执行日期和最终 commit 写入验收记录。
- [ ] Prompt 契约数字以定稿时重新生成的报告为准。当前仓库报告显示 30 项；历史文档中的其他数字未经复核不得混用。
- [ ] 区分当前参赛材料记录的 249 项后端测试和历史自查报告中的 169 项特定测试；不得相加为一个测试总数。
- [ ] 区分 18 套工程回归用例与 5 套参赛展示场景。
- [ ] 保留“未完成真实模型 API 联调、未评估真实视频准确率/误报率/召回率”的限制，除非团队确实补做了相应实验并保存证据。

## 三、研究结论与原创边界

- [ ] 所有实验数字都能追溯到生成脚本或报告文件。
- [ ] 同输入对照中的 8/10 和 10/10 明确写成“合成处置预期符合计数”，没有写成真实视频准确率。
- [ ] 64 种关系回答组合的穷举范围说明清楚，不写成所有可能输入或所有论证图的完全穷举。
- [ ] 4 类论证攻防场景说明为独立工程 fixture，不与五套展示案例混为一谈。
- [ ] 说明 PEAD grounded 求解目前只用于危险行为诱导专项策略；其余九类深度不同。
- [ ] Grounded 语义、PyArg、NetworkX 和其他第三方组件没有被写成团队原创算法。
- [ ] 原创贡献准确落在视频证据映射、事件作用域、来源合并、关系门控、规则配置与校验、人工复核、报告和验证链路上。
- [ ] 没有把“模型观察”写成独立验证事实，也没有把“未发现线索”写成视频整体安全保证。
- [ ] 不声称已证明真实准确率、误报率下降、召回率提升、生产级安全或比赛获奖水平。

## 四、文档完整性检查

- [ ] 项目简介讲清背景、痛点、目标、贡献、结果与边界。
- [ ] 设计方案讲清架构、模块职责、证据对象、PEAD 流程、规则保护、失败路径和隐私设计。
- [ ] 测试与验证讲清实验设计、输入来源、对照条件、实际结果、局限与复现命令。
- [ ] 演示脚本给出逐步操作、讲解词、预期输出和异常预案。
- [ ] 截图清单中每张图都有来源、目的、图注边界和验收状态。
- [ ] 运行与复现说明包含环境、安装、启动、合成演示、测试、故障排查与已知限制。
- [ ] 演示数据与图注规范区分合成输入、真实 UI 截图、独立机制图和示意图。
- [ ] 删除或解决所有 REPLACE、TODO、待确认、草稿提示和内部讨论内容；若仍有未完成项，不得把文件标成最终版。
- [ ] 术语、字段名、枚举、图号、表号、参考来源在全套材料中一致。
- [ ] 章节之间有必要的解释和过渡，避免只堆表格、名词和代码路径。

## 五、图片、PDF 与可读性检查

- [ ] 架构图、机制图、同动作对照、跨事件冲突和报告截图均与最终代码/数据一致。
- [ ] 每张图片都明确标注真实界面截图、合成输入结果、独立工程 fixture 或示意图。
- [ ] 不将合成结构化时间线标成原片截图。
- [ ] 所有截图在 PDF 实际显示尺寸下清晰可读；图注紧邻图片。
- [ ] 中文字体嵌入正常，无乱码、缺字或方框字。
- [ ] 表格不越界、不裁切，图片不拉伸，目录和页码正确。
- [ ] 图号、表号、正文交叉引用、参考文献和链接都有效。
- [ ] PDF 文字可选择和搜索；文件大小、页数、命名符合赛事要求。
- [ ] 检查 PDF 元数据、文件属性、截图和附录是否泄露身份或敏感信息。

## 六、程序包与现场演示检查

- [ ] 在干净环境中从零安装并启动，不依赖开发机残留文件。
- [ ] 后端和前端端口、API 地址、ffprobe 路径与说明文档一致。
- [ ] 无 API Key 时能明确演示合成场景，且不把合成结果冒充真实模型结果。
- [ ] 真实服务未配置或调用失败时，系统应明确报错/复核，不能静默显示成功。
- [ ] 合成场景、SQLite 记录和 HTML 报告均能按说明查看；离线包内部链接有效。
- [ ] 程序包中不包含密钥、真实敏感视频、开发机数据库、缓存或临时文件。
- [ ] 准备一套经过验证的备用截图和离线机制报告，但明确标注其来源。
- [ ] 答辩人能够解释原创边界、64 组穷举、10 场景对照、上游假设和真实评估缺口。
