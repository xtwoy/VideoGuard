# 视鉴 VideoGuard-E：前端梳理与美化交接

整理日期：2026-10-17。本文依据当前工作区代码和实际演示截图，不以旧提交或早期设计稿为准。

## 1. 给接手工具的任务

请美化“视鉴 VideoGuard-E”的现有中文视频审核工作台。交付可运行的 Next.js 前端，改善页面布局、信息层级、字体、颜色、组件、交互反馈和响应式体验。可以重新安排卡片、导航和操作区，保留现有业务能力、HTTP API 与审核结果语义。

产品定位：面向短视频创作者、运营人员及人工审核人员的内容安全辅助工具。用户提交视频后查看审核结论、定位证据、人工核查并执行整改；PEAD 是证据约束与决策模块。当前另有无需模型密钥的合成场景演示。

设计关键词：清晰、专业、可信、适合中文阅读、适合投屏演示。视觉风格可以重新设计；建议以内容为中心，保持状态区分明确。无需把现有靛紫主色、卡片排列或英文眉题当成必须保留的设计要求。

本次是前端美化交接，不增加登录、订阅、团队空间、历史列表、批量审核等后端尚未支持的产品功能。不要把项目改成宣传落地页。

## 3. 当前页面结构

```text
页头：视鉴 / VIDEOGUARD-E + 服务连接状态
页面介绍：视频内容审核 + 辅助审核提示
工作区
  提交区
    本地视频预览（未生成记录时）
    选择文件、可选标题、授权勾选、开始审核
    演示场景选择、场景说明、运行演示
  结果区
    加载 / 成功 / 错误消息
    结构化报告 ↔ HTML 报告
    当前 Mock 场景说明，或真实上传的本地播放器
    结论概览 | 分镜结果 | 问题与证据 | 整改与总结
页脚
```

初始桌面布局为较宽的提交区与空结果区；有结果后变成 300px 提交栏和宽结果区。当前最大内容宽度 1440px，940px 以下改单列，620px 以下进一步调整。

当前文件选择使用原生 input 和虚线框，**尚未实现拖放上传**。如界面写“拖入视频”，必须同时实现拖放交互；否则保持“选择文件”的准确文案。

### 提交与本地预览

- 支持 MP4 / MOV / WebM，大小上限 6,000,000 字节，时长上限 180 秒。
- 文件在浏览器通过 Object URL 预览，切换文件时释放旧 URL 并清空旧结果。
- 标题可选，最长 100 字；真实提交要求勾选处理授权。
- 文件类型、容器和时长最终由后端检查。不能仅靠 UI 显示“校验通过”。
- 请求期间禁止重复提交，给出处理反馈。后端没有阶段进度 API，不能显示虚构的精确进度百分比或假装收到逐阶段事件。

### 结论概览（`brief`）

显示总评标签、报告摘要、检查策略数、证据线索数、待处理项数、内容摘要、观察覆盖和处置一览。

这里的“检查策略”当前为十类风险策略；“维度评分”属于报告另一套结构，两者不能混用。统计卡的数值来自结果数据，不是营销统计。

### 分镜结果（`shots`）

显示每个分镜的 ID、开始/结束时间、场景摘要和事实数量。现有页面没有真实缩略图或抽帧图片；不要为合成场景配上看似真实的视频帧。

点击分镜会更新选中状态；有对应本地视频时跳转播放。Mock 或历史记录无原视频时，只能展示结构信息。

### 问题与证据（`audit`）

按三个部分组织：需要处理的风险项、事件级审计、全部证据。

每个风险项保留类别、内容判断、处置建议、原因、支持证据和反证引用。证据包含 ID、时间、模态与脱敏描述。可改成主从列表、分组卡片或详情抽屉，但不能只留一个风险分数。

### 整改与总结（`summary`）

包括总评及处理方向、五维度评分和子项、按事件/全局组织的问题与整改、局限说明。

五维度为：审核覆盖、证据可追溯性、风险控制、语境完整性、音视频可读性。

每项整改保留问题优先级、证据、时间范围、动作、建议内容和验收标准。可以用折叠、锚点、分栏改善长页阅读；不能把重要整改隐藏到难以发现的位置。

### HTML 报告

通过服务端 URL 在 iframe 中展示，并提供新标签页打开。当前服务端响应是 `inline`，页面没有单独实现浏览器附件下载按钮；可通过独立页面保存报告。美化时保留现有打开能力，不要把无行为的“下载”图标当成功能。

## 4. 必须保留的状态含义

| 结果 | 推荐用户可见含义 |
| --- | --- |
| `SUPPORTED / FLAG` | 有证据支持的疑似风险，标注关注；不直接等于违法 |
| `CONFLICTED / REVIEW` | 语境或证据冲突，需要人工复核 |
| `INSUFFICIENT / REVIEW` | 证据不足，需要人工复核 |
| `VERIFY_EXTERNAL` | 需要核实资质或其他外部事实 |
| `UNKNOWN / RECHECK` | 观察不完整或无法判断，需要补充观察 |
| `RETRY` | 需要重试 |
| `NOT_SUPPORTED / NONE` | 当前输入没有支持证据，不等于绝对安全 |

总评还有 `PUBLISHABLE`、`NEEDS_REVISION`、`BLOCKED`、`MANUAL_REVIEW`；它们与风险项的 judgement/disposition 不是同一个字段。

建议风险用红色、待处理/未知用琥珀色、已检查无处理项用克制的绿色或中性色。状态必须有文字，不依赖颜色或图标单独传递信息。

`LIVE` 与 `DEMO` 必须可区分。Mock 场景使用冻结上游输入，PEAD 实际执行；不能美化成“已完成真实视频分析”。Mock 不要求素材授权勾选，也不会调用外部模型。原视频缺失时应明确说明，禁用回看操作但仍保持证据文字可读。

## 5. API 与 URL 契约

所有通信使用 HTTP/HTTPS；用户明确要求不尝试 WebSocket。前端不直连外部模型或持有模型密钥。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/health` | 服务连接状态 |
| GET | `/api/demo/cases` | `{ cases: [{ id, title, description }] }` |
| POST | `/api/demo?case={id}` | 生成并保存选定场景结果，返回 ReviewRecord |
| POST | `/api/demo` | 当前仍有综合合成示例入口 |
| POST | `/api/reviews` | FormData：`video`、`title`、`consent` |
| GET | `/api/reviews/{id}` | 返回已保存的 ReviewRecord |
| GET | `/api/reviews/{id}/report` | 独立 HTML 报告 |

核心结构：

```ts
type ReviewRecord = {
  id: string;
  video_name: string;
  mode: "LIVE" | "DEMO";
  status: "DONE" | "ERROR";
  result: ReviewResult;
};
```

完整 `ReviewResult`、`Finding`、`Observation`、`AuditReport` 等类型以结果组件源码为准。旧交接包曾包含 8 个工程回归场景的数据，**不属于**当前五个参赛展示场景。独立设计预览应以 `backend/reports/demo-showcase/records.json` 的五条合成记录为输入。独立设计预览可用 Mock 数据适配层，整合回项目时必须恢复真实 API 路径，不能在生产组件里写死结论。

错误可能是 `detail: string`，也可能是 `detail: { message, review_id }`。后者需要保留失败记录/报告的查看入口。

API 地址优先级：URL 参数 `api` → `NEXT_PUBLIC_API_BASE_URL` → `http://127.0.0.1:8000`。

支持的链接参数：

- `review`：查询已有审核记录；其 ID 只在对应本地数据库中有效。
- `tab=brief|shots|audit|summary`：打开对应标签。
- `view=html`：初始化为 HTML 视图；当前点击视图切换按钮不会写回此参数。

成功提交会写入 `review`，点击标签会写入 `tab`。保留可刷新、可定位的行为。刷新后的历史记录不包含原始视频，不能显示成仍可播放。

## 6. 视觉问题与建议优先级

以下是设计建议，不是已实现功能：

| 优先级 | 当前问题 | 建议方向 |
| --- | --- | --- |
| 高 | 初始预览空框与结果空框占据大量空间，演示入口偏下 | 收紧初始态，让上传和演示两个入口在常用桌面首屏可发现 |
| 高 | 有结果后提交栏仍很突出，争夺结果注意力 | 让结论与待处理项成为视觉中心，提交区可以收纳或缩小 |
| 高 | 正文大量使用 10–12px 字号，证据禁用后整体变淡 | 提高关键文字字号与对比度；只弱化不可用操作，保留内容可读性 |
| 高 | 整改页同时铺开全部评分子项，关键动作在很下方 | 将整改优先级和行动建议前置；评分详情按需展开 |
| 中 | 场景下拉选择不容易理解各案例差异 | 用紧凑场景卡或分组选择器，让“冲突／隐私／观察不足”清楚可辨 |
| 中 | 卡片、边框、英文眉题较多，层级接近 | 统一标题与间距，减少没有信息价值的装饰层 |
| 中 | 未连接、连接中、失败状态不够鲜明 | 初始连接状态使用中性提示，失败提供可理解的反馈 |
| 中 | Mock 页面仍出现“点击可回看”等通用提示 | 按有无原视频切换提示，避免看起来可点但没有效果 |
| 中 | 一些按钮/标签缺少明确键盘焦点表现 | 完善焦点、hover、selected、loading、disabled 和错误态 |

建议桌面以 1440/1600px 为主要设计画布，同时检查 1024px、768px 和 390px；小屏阅读顺序应当是结论 → 关键问题 → 证据 → 建议。页面不出现无意义的横向溢出。

可以去掉页脚的框架技术列表、缩减装饰性英文，但保留品牌、审核用途、重要来源与状态提示。无需引入在线字体、CDN 图标或远程图片才能正常显示。

## 8. 修改范围与交付验收

默认修改 `frontend/`。接口字段、后端业务规则、冻结 fixture 输入、PEAD 算法和报告判定不属于视觉调整范围。可以新增前端组件与设计变量；必须解释新增依赖的用途。

接手仓库时先检查工作区，当前已有未提交改动。交接包保存的是当前工作区的源码快照，不要用旧提交覆盖新场景与新概览功能。

交付要求：

1. 返回实际可整合的 TSX/CSS 修改，保留**五场景选择**、上传提交、四标签、HTML 报告和错误路径。
2. 给出初始态、概览、同一动作立场对照、跨事件冲突证据、整改及移动端截图；观察不完整作为独立工程异常场景测试。
3. 通过 `npm run lint`（当前脚本实际是 `tsc --noEmit`）和 `npm run build`。
4. 检查长中文、缺失报告、空证据、部分覆盖、网络失败、无原视频等状态。
5. 更换 Mock 场景时结论、证据与整改随真实返回更新；不得写死前端展示结论。
6. 证据回看仅在关联原视频时可用；无视频时内容仍应可读。
7. 首屏和主要操作在常用桌面尺寸容易发现；移动端无页面级横向溢出；键盘焦点清晰。
8. 所有请求仅使用 HTTP/HTTPS；不要启动 WebSocket 浏览器调试或热更新连接。
