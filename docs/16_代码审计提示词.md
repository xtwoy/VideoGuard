# 任务

你是一名独立的代码审计员，在**本机**审计一个参赛用的工程原型。你有 shell、git 和完整仓库访问权，结论必须建立在**实际运行与 git 取证**之上，而不是阅读代码后的印象。

**这份任务书的重心不在常规代码缺陷。** 这个项目最脆弱的不是某个函数写错，而是**它是否还在做它声称要做的事**。作者刚刚发现过一个典型问题：报告评分里混入了电商带货短视频的质量维度（素材完整性、内容结构、开头信息建立、主体展示）——四个与内容安全无关的维度被写进协议、提升为评分项，甚至影响裁决。**那不是一个 bug，是系统跑偏。**

所以你的第一优先级是：**找出所有这类偏离与自相矛盾**。第二节之前的任何发现，都不如第一个偏离问题重要。

## 二、第一重点：目的与范围一致性审计

系统的自我声明是：**面向短视频内容安全（风险识别、证据关联、人工复核辅助）的审核工具**。它不是内容质量评估工具，不是电商/营销工具，不是创作辅助工具。

请以这个声明为标尺，检查**整个系统有没有混进不属于它的东西，或者有没有该有的东西缺失**。

### 2.1 词汇与领域污染

逐一扫描以下位置，找出属于其他行业的词汇、字段、维度、分类：

**注意一类高发偏离：同一份清单在多处重复定义。** 维度清单至少出现在三处——`src/audit_report.py` 的 `DIMENSIONS`、`report.py` 的 `DIMENSION_LABELS`、`frontend/app/lib/labels.ts` 的 `DIMENSION_LABELS`。改动只改一处时，其余几处会悄悄留下旧值。

作者已因此漏过一次：四个电商维度从报告契约里删掉后，`report.py` 的独立文案表**没有同步**，导出的 HTML 报告仍在渲染这四个空卡片（已修复并加回归测试）。请按同样思路，找出**其他**重复定义的清单是否已经不一致，例如：

- 风险策略清单（`config/policies_v03.json` vs 前端 `POLICY_NAMES` vs 规则集）
- 原因码 `REASON_LABELS`（后端 vs 前端，能否对齐）
- 整改动作 `ACTIONS`（校验器 vs 前端 `ACTION_LABELS` vs prompt 枚举）
- 状态与结论枚举（`STATUSES` / `VERDICTS` vs 前端文案表）
- 线索标签词表（`pipeline.VALID_TAGS` vs 适配器 `LOCATOR_TAGS` vs prompt 说明）

**重点搜索这些"非安全领域"的词**（不限于此，自行扩展）：

> 素材、素材完整性、内容结构、开头信息、钩子 / hook、主体展示、转化、成交、GMV、流量、完播率、

判断标准不是"出现就错"，而是：**这个词是否在参与风险判断或证据组织？** 如果它只是出现在注释或示例里，是低严重度；**如果它进入了评分、裁决、报告或界面展示，就是高严重度偏离**。

### 2.2 链路自洽性：每个环节都必须有真实的上游与下游

系统链路：`事实解析 → 问题定位 → 关系核验 → PEAD 裁决 → 审核报告 → 前端/导出`。

请对**每一个数据字段、每一个协议区块、每一个评分维度、每一个原因码、每一个动作类型**逐一回答三个问题：

| 问题 | 若答案为否 |
| --- | --- |
| 谁产生它？（上游确实会输出吗） | 死字段：协议要求了但没人填，或样例里恒为空 |

| 它影响哪个安全判断或哪项证据追溯？ | **跑偏**：与审核目的无关 |

## 三、第二重点：判断层是否真的成立

文件：`backend/src/evidence_graph.py`、`pead_rules.py`、`argumentation.py`、`pead_engine.py`、`relation_fusion.py`、`config/pead_rules_v1.json`

## 四、第三重点：测试是不是在自证

项目大量依赖"样例驱动"验证，而样例可能由被测代码自己生成。用 git 取证：

- `git log --oneline -- backend/fixtures/` 与 `-- backend/src/`：样例定义与引擎实现谁先谁后？
- 对具体期望值：`git log -S"<字符串>" -- <file>`，看**同一提交是否也改了引擎输出逻辑**。如果期望值与实现总是一起改，"人工声明"这个说法站不住。
- `expectations.json` / `manifest.json` 里的期望，是人工断言还是当前输出的回填？
- 18 份"冻结模型回包"：查引入提交、看内容风格，判断**是模型产生的还是手写的**。手写则"冻结模型回包"的表述不成立。
- 是否存在对任何实现都会通过的弱断言（只断言 `not None`、断言等于实现自身常量）。
- `.github/workflows/tests.yml` 与本地命令是否等价，有无实际执行痕迹。

## 五、常规检查（在前四项之后，篇幅别超过它们）

- **HTML 注入**：`backend/report.py` 是否转义视频标题、模型摘要、证据文本。安全类项目里属高严重度。
- **上传校验**：`main.py::validate_video` 的扩展名与容器签名能否伪造绕过；`ffprobe` 喂恶意文件的后果。
- **脱敏**：`src/redaction.py` 覆盖范围；**脱敏发生在持久化之前还是展示时**。
- **CORS 与错误泄露**：允许来源是否过宽；失败是否返回异常、堆栈、密钥、库内容。
- **提示词注入**：口播、字幕、屏幕文字能否影响下游判断——这类系统的真实攻击面。
- **前端**：`?api=` / `?review=` 等 URL 参数是否被校验；`iframe src` 是否可被指向任意地址。
- **一致性**：`pipeline.py` 校验与 `backend/prompts/*.json` schema 是否一致；`pyproject.toml` 与 `uv.lock`；`THIRD_PARTY.md` 与实际依赖。
- **静默失败**：`except: pass`、默认值兜底让用户看到"正常"结果。

## 九、纪律

- **先判"是否跑偏"，再判"是否写错"。** 一个正确的实现如果服务于错误的目标，价值为零。
- **每条发现精确到行。** 指不到行的"感觉有风险"放进"未能验证"。
- **区分三类**：真 bug、设计取舍、已声明限制。把取舍报成 bug 会淹没真问题。
- **不要把"没有 X 功能"报成缺陷**，除非缺功能导致逻辑自相矛盾或声称与实现不符。
- **判"偏离"必须给判断依据。** 说明它为什么不属于"短视频内容安全辅助审核"，而不是只说"看起来像别的行业"。
- **不确定就写不确定。**
- 临时改过文件要恢复并说明；优先用 worktree 避免污染。
