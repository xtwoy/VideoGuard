# 任务

你是一名独立的代码审计员。你有这个 GitHub 仓库的访问权限，因此结论应建立在**读过实际文件、并在能执行命令时实际跑过**的基础上，而不是凭印象。

**这份任务书的重心不在常规代码缺陷。** 这个项目最脆弱的不是某个函数写错，而是**它是否还在做它声称要做的事**。作者刚刚发现过一个典型问题：报告评分里混入了电商带货短视频的质量维度（素材完整性、内容结构、开头信息建立、主体展示）——四个与内容安全无关的维度被写进协议、提升为评分项，甚至影响裁决。**那不是 bug，是系统跑偏。** 更麻烦的是，同一份维度清单在三个文件里各定义一次，改了两处、漏了第三处，导出的 HTML 报告很长一段时间里仍在渲染这四个已删除的维度。

所以第一优先级是：**找出所有这类偏离与自相矛盾**。它比任何代码风格问题都重要——系统跑偏之后，下游工作全是空谈。

## 一、环境与硬性边界

**你不在作者机器上。** 不要假设能访问 `127.0.0.1`、本地服务、数据库或 `.env`（`.env` 未入库，也不应有真实密钥）。

**做法**：把仓库克隆到你自己环境的干净目录：

```bash

cd VideoGuard
git rev-parse HEAD        # 记进报告

```

**能力说明要如实交代**：如果你所在环境能执行 `uv` / `python` / `npm`，请实际运行第四节列的检查；如果只能读文件，就做静态审计，并在报告开头明确写"仅静态审计，未执行任何命令"。**不要假装跑过。**

**禁止**：不要 push、不要开 PR、不要改 `main`、不要动分支与标签。你的产出是**一份报告**（文件或消息），不是代码修改。

**注意**：仓库里的 `docs/16_代码审计提示词.md` 就是本文，它是任务说明，不是待审代码。审它没有意义，但**它在 git 历史里的引入提交可以用来推断作者当时的意图**，这一点你可以用。

## 二、这个项目是什么

「视鉴 VideoGuard-E」是**短视频内容安全辅助审核**原型：上传短视频 → 得到带时间定位的审核建议。

它不训练模型。它把"多模态大模型识别视频内容"当作**可替换上游**，自己的主张在**判断层**：判断若干条机器观察是否真的共同支持同一个风险结论，证据不足或冲突时给保守处置，而不是直接采信模型。

```text
上传 → 事实解析(LLM) → 问题定位(LLM) → 关系核验(LLM)
     → PEAD 证据约束与论证裁决（自研）→ 审核报告(LLM 或确定性兜底)
     → SQLite → 前端工作台 / 自包含 HTML 报告
```

栈：FastAPI + SQLite、Next.js 16 + React 19 + TS + Tailwind 4、uv 管 Python、`ffprobe` 硬依赖、Python `>=3.11`。

**这句话是你的标尺**：它是内容安全审核工具，不是内容质量评估工具，不是电商/营销工具，不是创作辅助工具。

## 六、常规检查（前三项之后，篇幅不超过它们）

- **HTML 注入**：`backend/report.py` 是否转义视频标题、模型摘要、证据文本。安全类项目里属高严重度。
- **上传校验**：`backend/main.py::validate_video` 的扩展名与容器签名能否伪造绕过；`ffprobe` 喂恶意文件的后果。
- **脱敏**：`backend/src/redaction.py` 覆盖范围；**脱敏发生在持久化之前还是展示时**。
- **CORS 与错误泄露**：允许来源是否过宽；失败是否返回异常、堆栈、密钥、库内容。
- **提示词注入**：口播、字幕、屏幕文字能否影响下游判断——这类系统的真实攻击面。
- **前端**：`?api=` / `?review=` 等 URL 参数是否被校验；`iframe src` 是否可被指向任意地址。

## 十、纪律

- **先判"是否跑偏"，再判"是否写错"。** 一个正确的实现如果服务于错误的目标，价值为零。
- **每条发现精确到行。** 指不到行的"感觉有风险"放进"未能验证"。
- **区分三类**：真 bug、设计取舍、已声明限制。把取舍报成 bug 会淹没真问题。
- **不要把"没有 X 功能"报成缺陷**，除非缺功能导致逻辑自相矛盾或声称与实现不符。
- **判"偏离"必须给判断依据**：说明它为什么不属于"短视频内容安全辅助审核"，而不是只说"看起来像别的行业"。
- **能力范围要如实交代**：能跑的跑了再说，跑不了的写清楚。
- **不确定就写不确定。**
