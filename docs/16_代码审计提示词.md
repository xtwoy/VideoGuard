## 二、这个项目是什么

「视鉴 VideoGuard-E」是**短视频内容安全辅助审核**原型：上传短视频 → 得到带时间定位的审核建议。

它不训练模型。它把"多模态大模型识别视频内容"当作**可替换上游**，自己的主张在**判断层**：判断若干条机器观察是否真的共同支持同一个风险结论，证据不足或冲突时给保守处置，而不是直接采信模型。

```text
上传 → 事实解析(LLM) → 问题定位(LLM) → 关系核验(LLM)
     → PEAD 证据约束与论证裁决（自研）→ 审核报告(LLM 或确定性兜底)
     → SQLite → 前端工作台 / 自包含 HTML 报告
```

栈：FastAPI + SQLite、Next.js 16 + React 19 + TS + Tailwind 4、uv 管 Python、`ffprobe` 硬依赖、Python `>=3.11`。

## 四、审计重点

### 1. 测试是不是在自证（最高优先级）

这个项目大量依赖"样例驱动"验证，而样例可能由被测代码自己生成。那样测试通过只证明代码与自身一致。

**你有 git，请用历史取证，而不是只看当前代码：**

- `git log --oneline -- backend/fixtures/` 与 `git log --oneline -- backend/src/`：样例定义的提交时间与引擎实现相比，谁先谁后？
- 对某个期望值，用 `git log -S"<具体字符串>" -- <file>` 找到它何时引入，再看**同一提交是否也改了引擎输出逻辑**。如果"期望值"和"实现"总是一起改，"人工声明"这个说法就站不住。
- `backend/fixtures/cases/<case>/expectations.json`、`manifest.json` 里的期望：是人工写的断言，还是从当前输出回填的？有什么区别可以验证（例如人工期望里应能看到与实现无关的独立推理）。
- `backend/fixtures/frozen_report_inputs.json` 冻结了 18 份 `audit_report_response.json` 的 SHA-256，作者称它们是"历史模型回包"。**请判断这批数据到底是模型产生的，还是手写的**——查引入提交、看内容是否与生成器风格一致、看是否有对应调用记录。如果手写，"冻结模型回包"这个表述不成立。
- `backend/tests/` 里是否存在对任何实现都会通过的弱断言（只断言 `not None`、断言等于实现自身常量、`assertTrue(result)`）。
- `.github/workflows/tests.yml` 与本地命令是否等价；工作流本身有没有实际被执行过的痕迹（例如提交信息、状态徽章、历史记录）。

### 2. PEAD 判断层（项目自称的核心）

文件：`backend/src/evidence_graph.py`、`pead_rules.py`、`argumentation.py`、`pead_engine.py`、`relation_fusion.py`、`config/pead_rules_v1.json`

- **规则集自我防护**：`pead_rules.py::RuleSet.integrity()` 声称"改配置无法绕过安全约束"。**请真的去绕**：复制配置到临时目录，尝试新增一条更高优先级规则、改 `FLAG` 规则的条件、或删掉某条保护规则，看校验是否会拦。**存在绕过路径即为高严重度。**
- **事件作用域**：`_same_event` / `_event` / `_scope_value`。构造 `referent_key` 碰撞、标识缺失的输入，检查是否串事件。
- **同源合并**：声称"同一份证据的多次描述不重复计为独立佐证"。验证 `source_refs` 签名能否被绕过（同内容不同 refs）。
- **攻击方向**：`argumentation.py` 把解释映射为 `attacks` 边喂给 PyArg grounded 求解。攻击方向是否符合论证语义？`UNDECIDED` 与循环的处理是否成立？
- **单调保守性**：`fixtures/truth_table.py` 声称验证"弱化某个回答不会使结论变强"。检查这个性质的**判定逻辑本身**是否可靠，有没有它测不到的输入。

### 3. 报告层

文件：`backend/src/audit_report.py`（约 874 行，最大单文件）、`backend/report.py`

- 五个维度固定为 `audit_coverage`、`evidence_traceability`、`safety_risk_control`、`context_completeness`、`audiovisual_readability`。检查 `_clean_dimensions` 的严格性、`_roll_up` 的"父级不得优于子级"是否真成立、`UNEVALUATED_SCORE` 分支会不会导致**缺证据却给出可发布结论**。
- 报告要求证据可回溯到毫秒。是否存在**证据与结论不匹配**、或时间范围可凭空构造的路径。
- **`backend/report.py` 生成的 HTML 是否转义**了视频标题、模型摘要、证据文本。这是安全类项目，**HTML 注入属高严重度**。

### 4. 安全与隐私

- **上传**：`main.py::validate_video` 依据扩展名与容器签名字节。能否伪造绕过？`ffprobe` 被喂恶意文件时行为如何？
- **脱敏**：`src/redaction.py` 覆盖手机号、邮箱、身份证等。有无常见格式遗漏？**脱敏发生在持久化之前，还是只在展示时**？
- **路径**：用户可控文件名是否参与路径拼接。
- **CORS**：`main.py` 允许来源是否过宽。
- **错误泄露**：失败路径是否把异常、堆栈、密钥、库内容返回前端。
- **前端注入**：`frontend/app/` 中是否有 `dangerouslySetInnerHTML`、把模型文本拼进 HTML、或对 `iframe src` / URL 参数（`?api=`、`?review=`、`?tab=`）缺少校验。
- **提示词注入**：上游文本（口播、字幕、屏幕文字）会流向下游。能否通过视频内容影响判断——这是这类系统的真实攻击面。

### 5. 工程一致性

- `pipeline.py` 的校验与 `backend/prompts/*.json` 的 schema 是否一致（字段、枚举、必填、`additionalProperties`）。
- 有无**声明支持但未实现**的能力，或**文档声称已验证、代码里没有对应验证**的地方。
- 失败是否被静默吞掉（`except: pass`、默认值兜底）而让人看到"正常"结果。
- `backend/pyproject.toml` 与 `uv.lock` 是否一致；`THIRD_PARTY.md` 的组件、版本、许可证与实际依赖是否吻合。
- 前端状态与 URL 是否会产生不一致；加载历史记录时"原视频不可回放"是否被正确处理。

## 八、纪律

- **每条发现必须精确到行。** 指不到行的"感觉有风险"放进"未能验证"，不要混进发现清单。
- **区分三类**：真 bug、有意为之的设计取舍、已声明的限制。把设计取舍报成 bug 会淹没真问题。
- **不要把"没有 X 功能"报成缺陷。** 这是参赛原型，范围由作者定义；除非缺功能导致逻辑自相矛盾，或声称与实现不符。
- **不确定就写不确定。** "看起来可疑但无法确认"照实写，不要为提高分量而断言。
- 若为验证临时改过文件，**恢复原状并在报告中说明动过什么**；优先用 worktree 避免污染。
