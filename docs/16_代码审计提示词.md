## 一、这是什么项目

「视鉴 VideoGuard-E」是一个**短视频内容安全辅助审核**原型：上传一段短视频，得到一份带时间定位的审核建议。

它不是模型训练项目。它把"多模态大模型识别视频内容"当作**可替换的上游**，自己的主张在**判断层**：判断若干条机器观察是否真的共同支持同一个风险结论，并在证据不足或冲突时给出保守处置，而不是直接采信模型。

处理链路：

```
上传视频 → 事实解析（LLM）→ 问题定位（LLM）→ 关系核验（LLM，按需）
        → PEAD 证据约束与论证裁决（本项目自研）→ 审核报告（LLM 或确定性兜底）
        → SQLite → 前端展示 / 导出自包含 HTML 报告
```

技术栈：FastAPI + SQLite（后端）、Next.js 16 + React 19 + TypeScript + Tailwind 4（前端）、uv 管理 Python 依赖。Python `>=3.11`。`ffprobe` 是硬依赖。

### 2. 验证测试是不是在自证

这是本次审计的**重点**。这个项目大量依赖"样例驱动"验证，而样例可能由被测代码自己生成——那样测试通过只证明代码与自身一致。

请具体检查：

- `backend/fixtures/` 下的期望值（`fixtures/cases/<case>/expectations.json`、`manifest.json`）是**人工声明的**，还是由 `backend/pipeline.py`、`backend/src/audit_report.py` 的当前输出**回填**的？如果是回填，测试实际在断言什么？
- `fixtures/generate.py --check` 只能发现"样例文件与生成器不一致"，**不能**证明生成器正确。这个循环论证的边界在哪里，哪些测试真正独立？
- `backend/fixtures/frozen_report_inputs.json` 冻结了 18 份 `audit_report_response.json` 的 SHA-256。这些回包声称是"历史模型回包"，但**它们真的是模型产生的，还是手写的**？如果是手写的，"冻结"这个说法是否成立？
- `backend/tests/` 里有没有断言过弱、或对任何实现都会通过的测试（例如只断言 `result is not None`、断言等于实现自身常量）？

### 3. PEAD 判断层（项目自称的核心贡献）

相关文件：`backend/src/evidence_graph.py`、`backend/src/pead_rules.py`、`backend/src/argumentation.py`、`backend/src/pead_engine.py`、`backend/src/relation_fusion.py`、`backend/config/pead_rules_v1.json`

重点核查：

- **规则集自我防护**：`pead_rules.py` 的 `RuleSet.integrity()` 声称"改配置无法绕过安全约束"。请尝试**构造绕过**：修改 `pead_rules_v1.json`（例如新增一条更高优先级规则、或改动 `FLAG` 规则条件），看能否在不触发校验的情况下让风险项变成放行。**如果存在绕过路径，这是高严重度问题。**
- **事件作用域**：`_same_event` / `_event` / `_scope_value` 用 `event_id` 与 `referent_key` 建立作用域。请构造两个事件在 `referent_key` 上碰撞、或缺失标识的输入，检查是否会串事件。
- **同源合并**：声称"同一份证据的多次描述不重复计为独立佐证"。请验证 `source_refs` 签名合并是否可被绕过（例如同内容但 refs 不同）。
- **grounded 语义使用是否正确**：`argumentation.py` 用 PyArg 的 grounded 求解，把攻击解释映射为 `attacks` 边。请检查**攻击方向**是否符合论证语义（谁攻击谁），以及 `UNDECIDED` 与循环的处理是否成立。
- **单调保守性**：`fixtures/truth_table.py` 声称验证了"弱化某个回答不会使结论变强"。请检查这个性质的**判定逻辑本身**是否可靠，是否存在它测不到的输入。

### 4. 报告层

相关文件：`backend/src/audit_report.py`（约 870 行，最大的单文件）、`backend/report.py`

- 报告维度固定为五个：`audit_coverage`、`evidence_traceability`、`safety_risk_control`、`context_completeness`、`audiovisual_readability`。请检查 `_clean_dimensions` 的严格性、`_roll_up` 的"父级不得优于子级"是否真的成立、以及 `UNEVALUATED_SCORE` 分支是否会导致**缺证据却给出可发布结论**。
- 报告包含支持证据与整改动作，且要求证据可回溯到毫秒。请检查是否存在**证据引用与结论不匹配**、或时间范围可以凭空构造的路径。
- `backend/report.py` 生成的独立 HTML：检查 **HTML 注入**（视频标题、模型返回的摘要、证据文本是否都经过转义）。这是安全类项目，注入属于高严重度。

### 5. 安全与隐私

- **上传处理**：`backend/main.py` 的 `validate_video` 依据扩展名与容器签名字节判断类型。请检查能否用伪造扩展名/魔数绕过，以及 `ffprobe` 被喂入恶意文件时的行为。
- **脱敏**：`backend/src/redaction.py` 标注手机号、邮箱、身份证等。请检查是否遗漏常见格式，以及**脱敏是否发生在持久化之前**（而不是只在展示时）。
- **路径与文件**：是否存在用户可控文件名参与路径拼接。
- **CORS**：`main.py` 的允许来源范围是否过宽。
- **错误泄露**：失败路径是否会把内部异常、堆栈、密钥、数据库内容返回给前端。
- **前端注入**：`frontend/app/` 中是否有 `dangerouslySetInnerHTML`、直接把模型文本拼进 HTML、或对 `iframe src` / URL 参数缺少校验的地方（`?api=`、`?review=`、`?tab=` 来自 URL）。
- **提示词注入**：模型输出会被喂给下一阶段。请检查上游文本（口播、字幕、屏幕文字）能否通过内容影响下游判断——这是这类系统的真实攻击面。

### 6. 工程一致性

- `pipeline.py` 的校验与 `backend/prompts/*.json` 的 schema 是否一致（字段、枚举、必填项、`additionalProperties`）。
- 是否存在**声明支持但实际未实现**的能力；或**文档声称已验证、代码里没有对应验证**的地方。
- 错误处理：失败是否可能被静默吞掉（`except: pass`、默认值兜底）而让用户看到"正常"结果。
- 依赖：`backend/pyproject.toml` 与 `backend/uv.lock` 是否一致；`THIRD_PARTY.md` 声明的第三方组件与实际依赖是否吻合，许可证声明是否正确。
- 前端：状态与 URL（`?review=` / `?tab=` / `?view=`）是否会产生不一致；加载历史记录时"原视频不可回放"是否被正确处理。

## 四、本项目已知且已声明的限制

以下限制作者已经承认并写进文档。**请不要把它们当作新发现重复报告**，但当你能证明"声明与实际不符"时请指出——例如文档说未联调，代码里却有伪造的成功结果。

1. **从未与真实大模型 API 联调**。所有验证基于冻结的、合成的上游输入。仓库里没有真实密钥，也没有真实回包（`fixtures/upstream_capture.py` 提供了采集工具，但未执行）。
2. **没有真实视频上的准确率、误报率、召回率**。任何"性能"数字都不存在，作者明确拒绝用合成数据冒充效果评估。
3. **上游四项假设未被真实验证**：事件带可用指向标识、线索与事件标识一致、引用事实真实存在、解析标记的反向语境进入线索。
4. **无法独立纠正上游遗漏**。若上游没报告警示，PEAD 看不到反证，可能误判。
5. **UI 上的"合成场景"是明确标注的演示**，不是真实视频审核结果。
6. 未做可执行打包分发；未验证与其他供应商的兼容性。

```markdown

## 发现清单
```

## 六、审计纪律

- **不要修改仓库代码**，只审。若为验证需要临时改动，恢复原状并在报告中说明你动过什么。
- **每条发现必须能指向具体行**。指不到行的"我觉得可能有风险"不要写进发现清单，可放到"未验证"里。
- **区分三类东西**：真 bug、有意为之的设计取舍、已声明的限制。把设计取舍报成 bug 会误导作者。
- **不要把"没有 X 功能"报成缺陷**。这是一个参赛原型，范围由作者定义；除非无功能导致逻辑自相矛盾或声称与实现不符。
- 如果某个地方你判断"看起来可疑但无法确认"，**如实写成这种状态**，不要为了提高报告分量而断言。

最后请给出一段**总体判断**：如果有人要基于这个仓库继续开发或对外声称它的能力，最需要先补的是什么。
