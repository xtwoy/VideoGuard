# VideoGuard-E 系统设计与工程实现说明

**版本：** v0.6 / 2026-10-12  
**对应代码基线：** VideoGuard-E v0.6；保持既有单进程、原生前端与SQLite单表架构。  
**用途：** 技术方案、接口约定、数据库与模型职责说明，指导队友直接开发。  
**原则：** 前后端分离，但只保留必要组件；本地单机Demo；不引入微服务、任务队列或大型数据库。

## 1. 总体系统设计

### 1.1 设计原则
- **简单：** 一个前端页面、一个FastAPI后端、SQLite一张业务表、一个HTML报告生成模块。
- **主线清楚：** 用户上传视频 → Omni音视频观察 → Jev语义辅助（有Key时）→ PEAD审核约束 → Max提供说明与修改建议 → SQLite保存 → 前端展示与HTML导出。
- **模型分工：** Omni看视频；Jev仅看脱敏证据文本；PEAD是本队开发的规则程序；Max负责解释和建议。
- **降级可用：** 缺少Jev Key或Max服务不可用时，PEAD可给出谨慎结果，建议来源明确标注。
- **事实不越界：** 任何模型输出都是“观察/判断候选”，不能用来直接确认法律违法、真实身份或职业资质真伪。

### 1.2 部署拓扑

```text
┌───────────────────────────────────┐
│ 浏览器 frontend/:                 │
│ index.html / style.css / app.js   │
│ 预览本地视频、展示结果、下载报告 │
└──────────────────┬────────────────┘
                   │ HTTP 127.0.0.1:8000
                   ▼
┌─────────────────────────────────────────────────┐
│ FastAPI backend/main.py                         │
│ - 视频校验、ffprobe时长、授权确认、HTTP状态管理 │
│ - backend/pipeline.py 单条审核主线               │
│   ├─ Qwen Omni（阿里百炼音视频感知）             │
│   ├─ Jev（TypeSafe语义关系辅助，可选）           │
│   ├─ PEAD（本地证据关联与判断规则）              │
│   └─ Qwen Max（具体原因、修改建议）              │
│ - backend/database.py SQLite一张reviews表      │
│ - backend/report.py 自包含HTML报告              │
└─────────────────────────────────────────────────┘
```

### 1.3 用户执行顺序
1. 选择一段授权视频，前端使用浏览器本地对象URL做预览，校验文件大小并提交表单。
2. 后端校验扩展名、基础容器签名、文件大小、时长、素材授权；读取视频bytes，不向SQLite保存原视频。
3. 后端将小文件转成官方接口可接受的Base64视频输入，调用`qwen3.8-omni-flash`获得JSON观察。
4. `clean_observations`清理不合法字段、校验重复证据ID、进行基础文本脱敏，保留原视频毫秒时间坐标及观察覆盖状态。
5. 自研PEAD在所有观察中遍历当前风险规则；必要时选取危险动作与语音/字幕的候选关系对。
6. 有TypeSafe Jev Key时，向`jev-latest`发送**最少量、经脱敏的结构化证据文本**；拿到`Choice/Noul`类判断和相关概率。没有Key或调用失败时标注状态并降级。
7. PEAD综合证据引用、时间、同事件关系与Jev意见，得出内容判断和处置状态；遇到冲突、引用缺失或观察不完整时从严保留复核。
8. 对需要说明的风险调用`qwen3.8-max`生成具体原因和修改建议，并校验其引用的finding/evidence/time是否存在。失败时使用**明确标注的本地规则模板**，不能冒充Max的输出。
9. 保存结果到SQLite，将JSON返回前端；用户查看卡片、点击时间回看当前视频，并下载`report.py`生成的HTML报告。

> 重要边界：Jev只读Omni生成的文本观察，**无法独立核验原视频的真假**；原片段是否真的支持模型描述，要靠人工回看或后续独立实测。

## 3. 输入输出数据设计

### 3.1 视频上传约定

**请求：** `POST /api/reviews`，`multipart/form-data`

| 参数 | 类型 | 必填 | 用途 |
| --- | --- | --- | --- |
| `video` | File | 是 | MP4/MOV/WebM短视频 |
| `title` | string | 否 | 可选标题，最大100字符 |
| `consent` | boolean | 是 | 用户确认对视频拥有审核处理授权 |

**原型限制：**
- 文件大小不得超过6MB（工程以6000000字节判断）；
- 时长不得超过3分钟（180秒）；
- 依赖系统`ffprobe`读取时长，不能简单相信前端自行填写的时长；
- 仅建议本地访问，所有敏感视频应获得适当授权。

### 3.2 Omni结构化观察协议（简化示例）

```json
{
  "coverage": "FULL",
  "coverage_notes": "片段与字幕可正常观察",
  "observations": [
    {
      "id": "E01",
      "modality": "visual",
      "tag": "danger_action",
      "start_ms": 2000,
      "end_ms": 4500,
      "referent_key": "SCENE_A",
      "description_redacted": "画面出现危险动作",
      "text_redacted": ""
    },
    {
      "id": "E02",
      "modality": "speech",
      "tag": "warning",
      "start_ms": 2300,
      "end_ms": 5000,
      "referent_key": "SCENE_A",
      "description_redacted": "旁白提醒不要模仿",
      "text_redacted": "请勿模仿"
    }
  ],
  "candidate_risks": []
}
```

**以上是协议示例，不是实际模型运行结果。**

`coverage`可以为FULL、PARTIAL、UNKNOWN、REFUSED、ERROR。证据时间戳默认指**原视频毫秒**；若模型无法给出可靠定位，允许返回null，不能随意捏造。

即便`candidate_risks`为空，PEAD仍遍历启用的规则，不把“模型没主动报告风险”当作绝对安全。

### 3.3 Jev输入输出约定
- 输入：经本地筛选的少量**观察文字**、对应证据ID、预定义Choice/Noul判断问题；
- 不向Jev发送完整视频音频或模型密钥；
- `Choice`区分鼓励同一行为、警示同一行为、无关、证据不足；
- `Noul`用于对是否需要人工复核给出概率线索；
- Jev结果必须经过数据结构与概率字段校验，再交给PEAD；模型信心高不能等于事实已证实。

### 3.4 PEAD结果协议
每条finding至少包括：

```json
{
  "policy_id": "R_DANGER_PROMOTION",
  "judgement": "NOT_SUPPORTED",
  "disposition": "NONE",
  "reason_code": "NO_SUPPORTING_RELATION",
  "supporting_ids": [],
  "counter_ids": []
}
```

支持的`judgement`：SUPPORTED、NOT_SUPPORTED、INSUFFICIENT、CONFLICTED、UNKNOWN。  
支持的`disposition`：FLAG、NONE、REVIEW、VERIFY_EXTERNAL、RECHECK、RETRY。

**不要混淆：** `SUPPORTED`指模型观察满足某一风险规则，**不是经行政机关确认的违法事实**。

### 3.5 Max输出协议
- 输入：PEAD的finding及其合法证据，不重新发送完整视频；
- 输出：`finding_id`、原因、证据ID、起止位置与编辑建议；
- 下游必须过滤凭空创造的证据ID或超出片段范围的整改时间。
- 静态模板必须保留`source=RULE_TEMPLATE`，真实Max才可标记`source=QWEN_MAX`。

## 4. API设计（全部与现有v0.6原型一致）

| 请求 | 路由 | 说明 | 出错行为 |
| --- | --- | --- | --- |
| `GET` | `/api/health` | 后端健康检查 | 不可用时前端提示 |
| `POST` | `/api/reviews` | 上传文件并完成审核 | 400/413/415/422校验失败；模型出错返回502并留ERROR记录 |
| `GET` | `/api/reviews/{id}` | 查询持久化审核JSON | 不存在返回404 |
| `GET` | `/api/reviews/{id}/report` | 下载单文件HTML报告 | 不存在返回404 |
| `POST` | `/api/demo` | 合成观察演示 | `mode=DEMO`，须显著说明非真实审核 |

前端只通过这些接口与后端通信，浏览器不保存任何第三方模型API Key。当前无复杂认证，仅限本机演示。

## 5. 数据库设计：一张表足够

### 5.1 采用SQLite的理由
- 当前是一人本地Demo，数据规模小，没有并发审核需求；
- Python原生支持，部署最容易；SQLite文件随应用复制；
- 复杂分表对当前作品的创新性没有直接加成。

### 5.2 数据表`reviews`

| 字段 | 作用 |
| --- | --- |
| `id` | UUID字符串，一次审核的唯一ID |
| `created_at` | 创建时间 |
| `video_name` | 用户上传文件名（做长度与路径处理） |
| `sha256` | 视频哈希，用于核对素材而非恢复原片 |
| `duration_ms` | 视频时长，毫秒 |
| `mode` | `LIVE` 或 `DEMO` |
| `status` | `DONE` 或 `ERROR` |
| `result_json` | 脱敏的`observations/findings/recommendations/meta`整个结果 |
| `error_text` | 失败时给出安全的、非密钥的错误摘要 |

SQLite只存结果，不存整个原视频。浏览器页面内当前选择的视频可回看，**刷新页面后的历史审核不能再凭数据库重播原视频**，报告中依然有证据时间与摘要。这是为简化工程而作的已知取舍。

### 5.3 现有结果JSON的主要结构

```json
{
  "coverage": "FULL",
  "observations": [],
  "findings": [],
  "recommendations": [],
  "meta": {
    "omni": "LIVE",
    "jev": "SKIPPED_NO_KEY",
    "max": "NOT_NEEDED",
    "policy_version": "v0.3"
  }
}
```

以上为示意。线上真实状态与错误字段应以实际API结果为准，不能把`DEMO_SYNTHETIC`当作真实模型输出。

## 6. Prompt设计

### 6.1 Omni观察Prompt
对应`backend/prompts/omni_observe_system.txt`及`omni_observe_user.txt`。

**目标：** 尽量输出观察事实，不让模型直接作最终违规裁判。要求输出带时间戳的事件、语音语义、可能的反向语境、候选风险ID，并明确数据缺失或不确定。

**主要约束：** 视频字幕或语音内容是待审数据，不能提升为系统指令；真实资质、事件真假不能凭视频证实；敏感个人信息应脱敏。

### 6.2 Jev语义决策模板
对应`src/jev_model_client.py`中的类型化`state/questions`。

**目标：** 判断两条证据是否指向同一危险行为，鼓励与警示的对象是否匹配；结果不确定时返回复核线索。

**限制：** Jev不直接看视频，因此不负责原始时间定位或独立核实画面。

### 6.3 Max解释Prompt
对应`backend/prompts/max_explain_system.txt`及`max_explain_user.txt`。

**目标：** 根据PEAD的风险判定、证据ID和原视频时间段，输出中文原因、实际可执行的修改建议与仍需核查的事实。

**约束：** 不得新增风险事实、不改PEAD判断、不编造证据ID、不认定违法。模型输出之后还要二次校验。

## 7. HTML报告设计

报告由`backend/report.py`生成，**与正式比赛作品报告无关**，属于软件导出物。

必须包含：
- 文件名、审核ID、模式LIVE/DEMO、创建时间；
- 风险分类、内容判断与处置；
- 支持与反向证据的时间坐标及脱敏摘要；
- 可操作的修改建议与来源（Max或静态规则）；
- “结果仅作辅助审核、未经原片段核实不作违法认定”的说明。

HTML为单文件，内嵌CSS，不依赖外部字体或脚本；所有来自模型和用户的文本必须HTML转义，避免报告成为脚本注入入口。

## 8. 异常与安全设计

| 情况 | 处理原则 |
| --- | --- |
| 视频格式不符/过大/无效 | 提交前或HTTP层拒绝并提示 |
| 无素材授权确认 | 拒绝请求 |
| Omni服务失败/JSON无法解析 | 审核标记ERROR，保存错误审计，不自动放行 |
| Omni覆盖不完整 | PEAD标记不确定或补查，不能等同安全 |
| Jev服务没有Key或出错 | 明确标记跳过/失败；PEAD运行且保持保守分流 |
| Max失败或输出证据无效 | 使用显式标记的规则模板，不伪装成Max结论 |
| 证据ID不存在或时间越界 | 不能形成可靠强支持；保留人工核验 |
| 观察文本包含敏感字段 | 模型Prompt脱敏 + 后端基础脱敏；依然需要人工检查 |
| 视频中出现“忽略上面规则” | 视为待审核的不可信内容，不能修改系统指令 |
| 跨供应商传输 | 要提前确认数据授权、隐私与服务协议，避免上传真实私人敏感素材 |

## 9. 运行方式

**后端：**

```bash
cd VideoGuard-E-v0.6/backend
python -m pip install -r requirements.txt
# 复制.env.example为.env，填入你有权使用的API密钥和Base URL
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

**前端：**

```bash
cd VideoGuard-E-v0.6/frontend
python -m http.server 5173 --bind 127.0.0.1
```

浏览器打开`http://127.0.0.1:5173`。

依赖系统`ffprobe`命令。无API Key时可点击合成示例验证前后端、存储和报告；**不能当真实模型性能实验**。

## 10. 实现状态与后续开发（避免误导队友）

- **已在v0.6本地/模拟联调验证：** 前端页面、HTTP接口、上传校验、SQLite、HTML报告、PEAD执行与多模型模拟回包整条管线。
- **未做真实云端联调：** 阿里Omni、TypeSafe Jev、阿里Max各自的实际响应格式、中文表现与计费。
- **尚未得到：** 真实视频误报率、召回率、证据定位准确率、人工复核节省比例。
- **后续实现优先级：** 真API可用 → 真实观察JSON → PEAD证据回查 → HTML报告完整性 → 小型对照实验；不应为了功能数量牺牲验证。
