# VideoGuard-E 系统设计与工程实现说明

**版本：** v0.6 / 2026-10-12  
**对应代码基线：** VideoGuard-E v0.6；保持既有单进程、Next.js前端与SQLite单表架构。  
**用途：** 技术方案、接口约定、数据库与模型职责说明，指导队友直接开发。  
**原则：** 前后端分离，但只保留必要组件；本地单机Demo；不引入微服务、任务队列或大型数据库。

## 1. 总体系统设计

### 1.1 设计原则
- **简单：** 一个前端页面、一个FastAPI后端、SQLite一张业务表、一个HTML报告生成模块。
- **主线清楚：** 用户上传视频 → 视频解析 → 问题定位/关系判断（按需）→ PEAD审核约束 → 问题汇总与整改建议 → SQLite保存 → 前端展示与HTML导出。
- **职责可替换：** 视频解析读取原视频；关系判断只读取最小化的脱敏证据；PEAD是本队开发的规则程序；问题汇总只解释既有判断。具体模型和供应商不是系统协议的一部分。
- **降级可用：** 缺少关系判断服务或问题汇总服务时，PEAD可给出谨慎结果，建议来源明确标注。
- **事实不越界：** 任何模型输出都是“观察/判断候选”，不能用来直接确认法律违法、真实身份或职业资质真伪。

### 1.2 部署拓扑

### 1.3 用户执行顺序
1. 选择一段授权视频，前端使用浏览器本地对象URL做预览，校验文件大小并提交表单。
2. 后端校验扩展名、基础容器签名、文件大小、时长、素材授权；读取视频bytes，不向SQLite保存原视频。
3. 后端将小文件转成适配器可接受的Base64视频输入，调用当前视频解析服务获得详细事实时间线。
4. `clean_video_parse`校验事实时间线；`clean_issue_locator`再校验问题定位结果对既有事件和事实的引用，进行基础文本脱敏并投影为 PEAD 证据，同时保留完整时间线。
5. 自研PEAD在所有观察中遍历当前风险规则；必要时选取危险动作与语音/字幕的候选关系对。
6. 配置关系判断服务时，仅发送**最少量、经脱敏的结构化证据文本**，用于判断鼓励、警示、无关或不确定；未配置或失败时标注状态并降级。
7. PEAD综合证据引用、时间、同事件关系与可选关系判断意见，得出内容判断和处置状态；遇到冲突、引用缺失或观察不完整时从严保留复核。
8. 对需要说明的风险调用问题汇总服务生成具体原因和修改建议，并校验其引用的 finding/evidence/time 是否存在。失败时使用**明确标注的本地规则模板**，不能冒充 AI 输出。
9. 保存结果到SQLite，将JSON返回前端；用户查看卡片、点击时间回看当前视频，并下载`report.py`生成的HTML报告。

> 重要边界：关系判断阶段只读视频解析阶段输出的最小化脱敏证据，**无法独立核验原视频的真假**；原片段是否真的支持模型描述，要靠人工回看或后续独立实测。

## 3. 输入输出数据设计

### 3.1 视频上传约定

**请求：** `POST /api/reviews`，`multipart/form-data`

| 参数 | 类型 | 必填 | 用途 |
| --- | --- | --- | --- |
| `video` | File | 是 | MP4/MOV/WebM短视频 |
| `title` | string | 否 | 可选标题，最大100字符 |
| `consent` | boolean | 是 | 用户确认对视频拥有审核处理授权 |

**原型限制：**
- 文件大小不得超过6MB（工程以6000000字节判断）；
- 时长不得超过3分钟（180秒）；
- 依赖系统`ffprobe`读取时长，不能简单相信前端自行填写的时长；
- 仅建议本地访问，所有敏感视频应获得适当授权。

### 3.2 视频解析 v2 协议

LLM 调用链使用四个职责协议：视频解析输出`videoguard_video_parse_v2`（完整镜头时间线、事实自身的毫秒范围、事实引用、shot 级可读性，以及素材完整性、结构、开头信息建立、主体展示、音画可读性五类全片分析）；问题定位输出`videoguard_issue_locator_v1`（`risk_cues`和限制）；可选关系判断输出`videoguard_relation_check_v1`；审核报告输出`videoguard_audit_report_v1`（九维评分、可回溯问题、证据、时间范围、整改动作和验收条件）。问题定位的每个线索必须引用视频解析中存在的`SHOT_ID:FACT_ID`和事件 ID，并把 cue 时间收敛到其实际引用的事实范围；旧视频解析协议直接拒绝。

后端先保存脱敏的完整时间线到`observation_detail`，再将`risk_cues`确定性投影为PEAD证据。PEAD不依赖模型给出的风险候选。

### 3.3 关系判断输入输出约定
- 输入：经本地筛选的少量**脱敏证据摘要**、对应证据ID、预定义Choice/Noul判断问题；
- 不发送完整视频音频或模型密钥；
- `Choice`区分鼓励同一行为、警示同一行为、无关、证据不足；
- `Noul`用于对是否需要人工复核给出概率线索；
- 关系判断结果必须经过数据结构与概率字段校验，再交给PEAD；模型信心高不能等于事实已证实。

### 3.4 PEAD结果协议
每条finding至少包括：

```json
{
  "policy_id": "R_DANGER_PROMOTION",
  "judgement": "NOT_SUPPORTED",
  "disposition": "NONE",
  "reason_code": "NO_SUPPORTING_RELATION",
  "supporting_ids": [],
  "counter_ids": []
}
```

支持的`judgement`：SUPPORTED、NOT_SUPPORTED、INSUFFICIENT、CONFLICTED、UNKNOWN。  
支持的`disposition`：FLAG、NONE、REVIEW、VERIFY_EXTERNAL、RECHECK、RETRY。

**不要混淆：** `SUPPORTED`指模型观察满足某一风险规则，**不是经行政机关确认的违法事实**。

### 3.5 审核报告输出协议
- 输入：已脱敏的视频解析、问题定位 observations、PEAD findings、事件级记录和解析阶段已定位的音画/结构问题；不重新发送原视频。
- 输出：`overall_verdict`、九项`dimension_scores`、按事件或全局分组的`revision_plan`、每个问题的证据与毫秒范围、每个动作的目标范围与验收条件。
- 报告模型不得改变PEAD的policy、judgement、disposition或reason_code；每个需要处理的 finding 必须进入一个结构化 issue。
- 下游校验所有事实/观察引用、finding ID、时间范围、issue/action 关联关系和总评一致性。非法或失败输出将被替换为同协议的受约束本地报告。

## 4. API设计（全部与现有v0.6原型一致）

| 请求 | 路由 | 说明 | 出错行为 |
| --- | --- | --- | --- |
| `GET` | `/api/health` | 后端健康检查 | 不可用时前端提示 |
| `POST` | `/api/reviews` | 上传文件并完成审核 | 400/413/415/422校验失败；模型出错返回502并留ERROR记录 |
| `GET` | `/api/reviews/{id}` | 查询持久化审核JSON | 不存在返回404 |
| `GET` | `/api/reviews/{id}/report` | 下载单文件HTML报告 | 不存在返回404 |
| `POST` | `/api/demo` | 合成观察演示 | `mode=DEMO`，须显著说明非真实审核 |

前端只通过这些接口与后端通信，浏览器不保存任何第三方模型API Key。当前无复杂认证，仅限本机演示。

## 5. 数据库设计：一张表足够

### 5.1 采用SQLite的理由
- 当前是一人本地Demo，数据规模小，没有并发审核需求；
- Python原生支持，部署最容易；SQLite文件随应用复制；
- 复杂分表对当前作品的创新性没有直接加成。

### 5.2 数据表`reviews`

| 字段 | 作用 |
| --- | --- |
| `id` | UUID字符串，一次审核的唯一ID |
| `created_at` | 创建时间 |
| `video_name` | 用户上传文件名（做长度与路径处理） |
| `sha256` | 视频哈希，用于核对素材而非恢复原片 |
| `duration_ms` | 视频时长，毫秒 |
| `mode` | `LIVE` 或 `DEMO` |
| `status` | `DONE` 或 `ERROR` |
| `result_json` | 脱敏的`observation_detail/observations/findings/audit_report/meta`整个结果 |
| `error_text` | 失败时给出安全的、非密钥的错误摘要 |

SQLite只存结果，不存整个原视频。浏览器页面内当前选择的视频可回看，**刷新页面后的历史审核不能再凭数据库重播原视频**，报告中依然有证据时间与摘要。这是为简化工程而作的已知取舍。

### 5.3 现有结果JSON的主要结构

```json
{
  "coverage": "FULL",
  "observations": [],
  "findings": [],
  "audit_report": {"schema_version": "videoguard_audit_report_v1"},
  "meta": {
    "video_parse": "LIVE",
    "relation_check": "SKIPPED_NO_KEY",
    "audit_report": "LIVE",
    "policy_version": "v0.3"
  }
}
```

以上为示意。线上真实状态与错误字段应以实际API结果为准，不能把`DEMO_SYNTHETIC`当作真实模型输出。

## 6. Prompt设计

### 6.1 视频解析 Prompt
对应`backend/prompts/video_parse_system.md`、`video_parse_user.md`与机器可校验的`video_parse_schema_v2.json`。关系判断和审核报告各有 system/user Markdown Prompt 与 JSON Schema。问题定位使用`issue_locator_jev_question.md`生成 JEV 原生 `state/questions` 请求，接收 `answers` 后映射到内部 `issue_locator_schema_v1.json`，不让供应商格式流入 PEAD 或报告。

**目标：** 先输出完整镜头时间线，再以事实引用建立事件，最后输出风险线索。解析阶段不作最终违规裁判；完整时间线保存在`observation_detail`，风险线索被确定性投影为PEAD可消费的证据。

**主要约束：** 视频字幕或语音内容是待审数据，不能提升为系统指令；真实资质、事件真假不能凭视频证实；敏感个人信息应脱敏。

### 6.2 问题定位/关系判断模板
对应`src/relation_client.py`中的类型化`state/questions`；当前实现可替换，文件名不构成流程协议。

**目标：** 判断两条证据是否指向同一危险行为，鼓励与警示的对象是否匹配；结果不确定时返回复核线索。

**限制：** 关系判断阶段不直接看视频，因此不负责原始时间定位或独立核实画面。

### 6.3 审核报告 Prompt
对应`backend/prompts/audit_report_system.md`及`audit_report_user.md`。

**目标：** 根据PEAD的风险判定、解析事实、内容分析问题、证据ID和原视频时间段，输出九维评分、按事件或全局内容项归组的问题、实际可执行的处理动作和验收条件。

**约束：** 不得新增风险事实、不改PEAD判断、不编造证据ID或时间范围、不认定违法。模型输出之后必须经过结构、引用、时间与总评一致性二次校验。

## 7. HTML报告设计

报告由`backend/report.py`生成，属于软件导出物。

必须包含：
- 文件名、审核ID、模式LIVE/DEMO、创建时间；
- 风险分类、内容判断与处置；
- 支持与反向证据的时间坐标及脱敏摘要；
- 可操作的修改建议与来源（问题汇总或静态规则）；
- “结果仅作辅助审核、未经原片段核实不作违法认定”的说明。

HTML为单文件，内嵌CSS，不依赖外部字体或脚本；所有来自模型和用户的文本必须HTML转义，避免报告成为脚本注入入口。

## 8. 异常与安全设计

| 情况 | 处理原则 |
| --- | --- |
| 视频格式不符/过大/无效 | 提交前或HTTP层拒绝并提示 |
| 无素材授权确认 | 拒绝请求 |
| 视频解析服务失败/JSON无法解析 | 审核标记ERROR，保存错误审计，不自动放行 |
| 视频解析覆盖不完整 | PEAD标记不确定或补查，不能等同安全 |
| 问题定位回包缺项/错类型/非法概率 | 整体失败并保存ERROR；不转换为无风险 |
| 关系判断服务没有配置、出错或回包非法 | 明确标记跳过/失败；PEAD运行且保持保守分流 |
| 问题汇总失败或输出证据无效 | 使用显式标记的规则模板，不伪装成模型结论 |
| 证据ID不存在或时间越界 | 不能形成可靠强支持；保留人工核验 |
| 观察文本包含敏感字段 | 模型Prompt脱敏 + 后端基础脱敏；依然需要人工检查 |
| 视频中出现“忽略上面规则” | 视为待审核的不可信内容，不能修改系统指令 |
| 跨供应商传输 | 要提前确认数据授权、隐私与服务协议，避免上传真实私人敏感素材 |

## 9. 运行方式

**后端：**

```bash
cd VideoGuard-E-v0.6/backend
python -m pip install -r requirements.txt
# 复制.env.example为.env，填入你有权使用的API密钥和Base URL
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

**前端：**

```bash
cd VideoGuard-E-v0.6/frontend
npm ci
npm run dev -- --hostname 127.0.0.1 --port 5173
```

浏览器打开`http://127.0.0.1:5173`。

依赖系统`ffprobe`命令。无API Key时可点击合成示例验证前后端、存储和报告；**不能当真实模型性能实验**。

## 10. 实现状态与后续开发（避免误导队友）

- **已在v0.6本地/模拟联调验证：** 前端页面、HTTP接口、上传校验、SQLite、HTML报告、PEAD执行与多模型模拟回包整条管线。
- **未做真实云端联调：** 当前接入的视频解析、关系判断和问题汇总服务的实际响应格式、中文表现与计费。

- **后续实现优先级：** 真API可用 → 真实观察JSON → PEAD证据回查 → HTML报告完整性 → 小型对照实验；不应为了功能数量牺牲验证。
