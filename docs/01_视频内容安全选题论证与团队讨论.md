# 视频内容安全选题论证与团队讨论稿

**用途：** 给队友和指导教师说明为什么考虑该方向，支持讨论后作出是否立项的决定。  
**性质：** 内部立项讨论稿，**不是参赛作品报告**。  
**建议工作题目：**《视鉴——基于全模态理解与证据约束的短视频内容安全辅助审核系统》。最终标题可根据实验结果调整。

## 一、我们准备解决什么问题？

我们不是做视频剪辑器，也不是让AI直接对视频宣布“违法”。

我们希望做一个**给创作者或内容审核人员使用的视频安全辅助工具**：

上传一段短视频，系统先理解画面、语音和字幕；发现疑似风险后，指出具体时间和可以回看的证据，区分行为本身与视频表达的立场；对证据不足、需要外部事实核实的情况要求复核；最后形成可操作的修改建议和HTML审核报告。

两个对比场景最能说明价值：

- **场景A：** 视频中出现危险动作，旁白是“请勿模仿，这是错误示范”。模型不能仅因为看到危险动作就把它认定为“鼓励危险行为”。
- **场景B：** 相近的动作画面配有“来挑战一下”的鼓励语。系统应识别传播语义与动作的关联，并指出发生时间。
- **场景C：** 主播身穿白大褂，自称医生并推荐某商品。系统可以指出“出现资质声称与营销话术”，但不能只凭白大褂或自称断言真实资质为假。

以上是**产品设计用的模拟场景**，不是已发生事件或已实现检测结果。

## 二、为什么选择“视频内容安全”而不只做AI生成内容检测？

### 1. 研究对象覆盖更广

视频内容安全面向**内容及传播风险**，与素材由真人拍摄、人工剪辑还是AI生成没有必然绑定关系。

人拍摄的危险模仿挑战、真人摆拍的虚假剧情、营销诱导、个人信息误曝光，同样可以形成内容安全问题。AI生成内容只是其中一个子领域。这样系统的实际用户更广，也避免与单一AI深伪检测问题绑定。

### 2. 现实治理需求明确，但不能机械理解政策

中央网信办在2026年5月部署规范短视频内容标注，要求平台提供虚构演绎、AI生成、营销、转载、个人观点、无需标注等必选标签，说明平台需要对内容和发布场景进行更规范的治理。

2026年9月30日的“清朗·整治短视频虚假人设乱象”专项行动进一步关注虚构职业资质、AI仿冒人物、摆拍编造冲突、营销误导等风险。

**我们的合理结论是：** 视频内容的真实性、传播语义、风险提示和审核流程有明确现实价值。

**不能过度外推的是：** 政策并没有证明“我们设计的算法一定有效”，也没有要求所有视频均交给某个AI模型自动判违规。我们的系统应聚焦**可观察证据、辅助审核和可追溯处置**。

来源：
- https://www.cac.gov.cn/2026-05/12/c_1780328273038196.htm
- https://www.cac.gov.cn/2026-09/30/c_1792520301987752.htm

### 3. 与本届比赛方向吻合

2026年研究生网络安全创新大赛创意作品赛明确覆盖**内容安全、智能安全**等开放方向，作品强调创新性、完整性、应用价值。视频风险审核属于典型内容安全应用方向。

来源（高校转载的2026赛事通知）：
https://gra.hnu.edu.cn/info/1050/10519.htm

### 4. 与我们现实资源相匹配

我们目前不适合训练视频基础模型或建立大型标注团队，也没有必要重新开发OCR、ASR和复杂抽帧算法。直接使用可调用的多模态模型Omni完成感知，将自研工作放在证据组合、风险判断边界、人工复核分流和报告上，更可能在截止日期前完成可运行的作品。

具体技术路线：
- 阿里Qwen Omni：理解音视频和时间信息；
- TypeSafe Jev：只接收必要的脱敏文本证据，协助判定“鼓励/警示/无关/不确定”；
- 自研PEAD：验证引用、时间、规则条件和不同模型之间的分歧；
- Qwen Max：根据前面形成的审核结果，生成原因与修改建议。

这里**自研贡献不是把四个模块串起来**，而是PEAD的可执行证据约束与审计流程。

## 三、为什么不是一个“套壳大模型”项目？

风险在于：如果直接“传视频给Omni → 返回违规标签 → Max写报告”，确实属于比较普通的大模型应用，难以证明研究创新。

已有SafeWatch（ICLR 2025）已经做到多类别视频内容安全审核、策略遵循和解释，说明该领域已有较成熟的研究。

因此，**我们必须选择一个小而具体的技术突破口**：

> **在视频中出现危险行为、伴随语音/字幕表达时，怎么验证这些证据确实在描述同一事件，且其传播含义到底是鼓励、警示还是其他情境？在证据不足时如何合理暂缓，而不是胡乱给出结论？**

我们的PEAD组件尝试完成：
1. 从Omni所有观察主动遍历风险规则，减少“模型忘记主动报出风险”的候选遗漏；
2. 以证据ID、时间范围、同一事件指向及Jev语义判断校验风险关系，不以单纯标签共现作为充分条件；
3. 将风险内容判断与处理建议分离，避免全部视频被简单分成“合规/违规”；
4. 对模糊情境和模型分歧保留回看与人工复核，并记录为什么这样处理。

**必须承认：** PEAD现在是一种待验证的候选改进方法，不应宣称全球首次；若对照实验显示其误报、漏报或复核负担并无明显收益，要据实调整创新主张。

研究参考：
https://proceedings.iclr.cc/paper_files/paper/2025/hash/beac6bfb7eac3d651307c16ac747df01-Abstract-Conference.html

## 四、为什么先聚焦两类，再逐步扩展？

| 方向 | 第一版定位 | 选取原因 |
| --- | --- | --- |
| 危险行为诱导及模仿 | **核心研究场景** | 可直接测试视频动作与旁白/字幕的关联，技术贡献明确 |
| 暴力行为画面及新闻、影视语境 | **核心对照场景** | 可检验正常报道、影视片段是否被简单误判 |
| 个人隐私泄露 | 扩展演示 | 检查单模态证据也能有效触发风险提示 |
| 营销用语和职业资质声称 | 扩展演示/外部核验 | 对应政策热点，但很多真假问题不能凭视频核定 |

**多类别是系统形态，不是必须每类都做复杂实验。**  
系统未来可以配置更多风险策略，但当前研发与实验资源先集中于前两类。

## 五、和其他可选项目的比较

| 候选方向 | 优势 | 当前主要问题 | 对我们适配度 |
| --- | --- | --- | --- |
| RAG知识库恶意指令注入 | 研究路径成熟，有开源基准，较易构建可重复测试 | 与此前期待的视频内容安全关注点不同，已有研究较拥挤 | 可做备选 |
| Deepfake真假视频检测 | 主题直观、关注度高 | 高质量数据、分布外泛化、模型训练与计算资源要求高；真实性难证实 | 当前不优先 |
| **视频多风险审核 + 证据约束** | 政策需求明显、演示直观、可复用Omni无需训练大模型 | 需解决“套壳”问题，并通过真实对照证明PEAD价值 | **建议优先** |
| 大型直播实时违规监控平台 | 产品化空间大 | 视频流并发、延迟、实时上下文要求明显超出当前资源 | 不做第一版 |

以上是团队内部基于现有资源的**定性判断，不是官方评审排序**。

## 六、我们要付出的成本和承担的风险

### 开发成本
- 普通笔记本可以开发Python与前端；
- 需要阿里云百炼模型调用权限与额度；
- Jev使用独立TypeSafe AI API Key，可选。若申请困难或中文效果不足，要允许跳过；
- 初版只审核上传的视频，最大6MB、3分钟，视频过大需压缩；
- 需要若干合规视频、人工标注时间段及技术讨论时间。

### 核心风险与应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| Omni漏掉短暂动作或给错时间戳 | 后续模型无法正确定位 | 显示“模型观察”，人工回看核验，不虚构精准定位 |
| Jev只能读文字观察，且服务独立 | 无法纠正Omni根本没看到的事实；联调可能受阻 | 保持PEAD可独立运行，优先小样本验证中文效果 |
| 模型误把安全教育判危险诱导 | 对正常内容产生误报 | 纳入“鼓励 vs 警示”的同源配对难例 |
| 全部模糊内容都转人工 | 虽然避免自动误判，但失去效率价值 | 同时统计风险识别质量与人工复核比例 |
| API费用/网络/密钥/隐私 | 演示失败或合规风险 | 本地接口联调、预算监控、合法素材、后端保管密钥；敏感素材慎用境外服务 |
| 最终效果没有优于基线 | 创新结论不能成立 | 准确披露结果，保留工程成果；必要时收缩研究主张 |

**使用TypeSafe的特别提醒：** 它是独立第三方服务。真实涉隐私视频和文本必须考虑跨服务、可能跨境传输与授权要求；不能默认把敏感原文传过去。本项目设计仅转交**脱敏的简短机器观察描述**。

## 八、可直接发给队友的讨论开场白

我们准备参加今年研究生网络安全创新大赛的创意作品赛，方向是内容安全。经过比较，我们倾向做一个短视频安全辅助审核系统，不局限于AI生成视频或未成年人。它直接利用阿里Omni理解原视频，通过TypeSafe Jev辅助判断鼓励/警示等语义关系，再用我们自己实现的PEAD规则引擎核查证据是否相关、何时需要人工复核，最后让Max生成修改建议与可导出的HTML报告。

选择它的原因是：有现实内容治理需求；普通电脑配合云端模型可实现；系统演示清楚；同时能围绕“视频证据是否真的支持风险结论”形成一个比较具体的研究问题。

但已有视频安全模型，因此调用大模型本身不算创新。我们需要一起确认API条件、合法测试素材、开发分工和实验计划，之后以真实结果决定创新点是否成立。
